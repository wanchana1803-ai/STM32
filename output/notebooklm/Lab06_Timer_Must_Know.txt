## ส่วนที่ 1 ความรู้ฝั่ง STM32

# Lab06_Timer: Timer และ Period

## เป้าหมายและพื้นฐาน

**เป้าหมาย:** สร้าง timebase ที่คำนวณได้ก่อนนำไปใช้ PWM

สำหรับ upcounter edge-aligned ที่ใช้ internal clock: `f_update = f_TIM / ((PSC+1)(ARR+1))` ต้องหา f_TIM จาก clock tree จริง เพราะไม่จำเป็นต้องเท่ากับ CPU clock และมีเงื่อนไข prescaler/TIMPRE ตามรุ่น

ตัวอย่างสมมติ f_TIM=16 MHz, PSC=15999, ARR=999 ได้ update 1 Hz ถ้า toggle LED ทุก update จะได้ LED ครบหนึ่งรอบทุก 2 วินาที

**ขั้นตอน:** เลือก timer ที่มีใน F410 → บันทึก clock source → คำนวณค่า → เปิด clock → ตั้ง PSC/ARR → โหลดค่าและจัดการ update flag ตามคู่มือ → start → ตรวจ update แบบ polling ก่อน

**ตรวจผล:** เปรียบเทียบ 100 ms และ 1 s กับการวัด อธิบายผลของการเปลี่ยน PSC เพียงตัวเดียว ระบุข้อจำกัด polling ที่อาจพลาดเหตุการณ์เมื่อ main ทำงานนาน

**คำถาม:** ต้องการ update 10 Hz ที่ f_TIM=16 MHz, PSC=15999 ใช้ ARR เท่าไร? เฉลย 99

**อ่าน:** RM0401 บท RCC และ TIM5; หนังสือบท 10–11

## ตั้งค่า STM32CubeMX

Lab เดี่ยวใช้ TIM5 Internal Clock, Counter Up; ตัวอย่าง f_TIM=16 MHz ตั้ง PSC=15999 ARR=999 ได้ update ทุก 1000 ms เริ่ม polling ก่อน; คง HAL timebase แยกไว้ และอย่าใช้ TIM5 ร่วม encoder ในโปรเจกต์รวมโดยไม่จัดสรรใหม่

ใช้ MCU STM32F410RB ที่ตรง package ของบอร์ด บันทึก `.ioc`, CubeMX/firmware package version และเลือก toolchain ที่ติดตั้งจริง ก่อน generate ให้เก็บ USER CODE และตรวจ diff หลัง generate ชื่อ handle ในตัวอย่างเป็นตัวอย่าง ต้องเทียบกับไฟล์ที่ CubeMX สร้าง

## เชื่อมกับรีจิสเตอร์

PSC แบ่ง clock; ARR กำหนดปลาย count; CNT ค่าปัจจุบัน; EGR โหลดค่าผ่าน update; SR.UIF ระบุ update

## ลงมือทีละขั้น

1. เขียนสูตร PSC/ARR และตรวจ clock tree ก่อน generate
2. เริ่ม timer และตรวจ CNT เดิน
3. ใช้ polling UIF ทดลอง 100/1000 ms โดย main ไม่มีงานบล็อก
4. จงใจเพิ่มงานช้าแล้วสังเกต UIF ไม่ใช่ counter จำนวน event
5. ถ้ารับ PERIOD จาก GUI ให้หยุด timer/reload/update/clear flag/restart ตามลำดับที่ตรวจแล้ว จึง ACK

## Pseudocode

clock → prescaler → counter → update flag → application; เปลี่ยน period ต้องจัดการค่า buffered และ pending

## ตัวอย่างแกนหลักและตำแหน่งเพิ่ม

ตัวอย่างประกอบแนวคิด ไม่ใช่ firmware เต็มหรือโปรเจกต์พร้อม flash ให้เพิ่มใน USER CODE ตามที่ระบุหรือไฟล์ application แยกหลัง generated init ห้ามคัด main ทับทั้งไฟล์ ยังไม่ได้ build กับ `.ioc` หรือทดสอบบอร์ดจริง

```c
/* USER CODE BEGIN 2 */
if (HAL_TIM_Base_Start(&htim5) != HAL_OK) { Error_Handler(); }
__HAL_TIM_CLEAR_FLAG(&htim5, TIM_FLAG_UPDATE);
/* USER CODE BEGIN 3: polling-only experiment */
if (__HAL_TIM_GET_FLAG(&htim5, TIM_FLAG_UPDATE) != RESET) {
    __HAL_TIM_CLEAR_FLAG(&htim5, TIM_FLAG_UPDATE);
    HAL_GPIO_TogglePin(LED_GPIO_Port, LED_Pin);
}
```

# Lab06_Timer — Python Tkinter

## เป้าหมาย

ตั้ง period และเปรียบเทียบ timestamp MCU กับ callback UI

เรียนพื้นฐาน Python/Tkinter จาก roadmap ก่อน บทก่อน Lab03 ใช้ mock; การเชื่อมบอร์ดจริงทุกบทต้องผ่าน Lab03 GUI และ Lab03 firmware รวมทั้ง HELLO/PING ตาม protocol.md (เอกสารประกอบในหลักสูตร)

## แนวคิดที่ใช้

after จัดตาราง UI ไม่ได้แทน hardware timer การวิเคราะห์เวลาต้องรู้ว่า timestamp มาจากฝั่งใด

Widgets: Spinbox 10–5000 ms, Apply, labels requested/confirmed, ตาราง timestamp

แยก requested, pending และ confirmed ตามความจำเป็น ใช้ StringVar/IntVar เป็นค่าของ view; protocol parser ตรวจข้อมูลก่อนให้ application state อัปเดต GUI

## ขั้นตอนปฏิบัติ

1. validate period เป็นจำนวนเต็มและส่งเฉพาะกด Apply
2. รอ ACK ก่อนยืนยันค่าใหม่
3. รับ TIMER telemetry ที่มี MCU ms/update_count
4. คำนวณ delta ด้วย unsigned wrap สำหรับ tick MCU แยกจาก received time ฝั่ง PC
5. ทำ UI tick ด้วย after แล้วทดลองลากหน้าต่าง/งานอื่นเพื่อดู jitter

## ตัวอย่างแกนหลัก

Snippet เพื่อใช้ระหว่างเรียน ไม่ใช่แอปเต็ม ชื่อ widget/state เช่น root/status และฟังก์ชัน application ที่เรียกต้องสร้างในขั้นตอนก่อนหน้า ในบทนี้ให้ Antigravity ช่วยเติมทีละส่วนและอธิบายเหตุผล

```python
def tick_delta_ms(new, old):
    return (new - old) & 0xFFFFFFFF

def ui_heartbeat():
    ui_tick.set(ui_tick.get() + 1)
    root.after(100, ui_heartbeat)
# 100 ms is a scheduling request, not a precise hardware period.

```

ให้ main thread เป็นผู้เรียกโค้ดที่เปลี่ยน widget ใช้ worker เฉพาะ transport; ห้ามเรียก serial read แบบรอไม่จำกัดจาก button callback Mock ต้องคืน response ตามคำสั่งและ session/id จริง ไม่เปลี่ยน GUI ให้ success โดยข้าม parser

## กรณีทดสอบ

- 10/1000/5000 ส่งได้และ 0/5001 ไม่ส่ง
- old=0xFFFFFFF0,new=0x10 ได้ delta=32
- UI delay ไม่ถูกบันทึกเป็น timer error ฝั่ง MCU โดยอัตโนมัติ

ทดสอบเพิ่มทุกบท: ปิดหน้าต่างขณะมี pending, ส่งข้อมูลผิดชนิด, reconnect และยืนยันว่าไม่มี callback/worker เก่ามาแก้ state ของ session ใหม่

## แบบฝึกหัด

ถ้า UART รวม 10 timer updates เป็น telemetry เดียวควรคำนวณ period อย่างไร?

แนวตอบ: ใช้ delta MCU time และ delta update_count ที่สอดคล้องกัน ไม่ถือว่าช่องว่างระหว่าง frame คือ period หนึ่งรอบ
